# WAudible journal

Newest entry first.

## 11 Nov 2026

- Added slow request logging (`app/request_log.py`). Every request is timed from before the login check, and one slower than 3 seconds writes a single WARNING line to the journal with the method, the route pattern (for example `/audio/<int:book_id>/<int:page>`, never the real path or query string), the status and the time. Database connect errors now write one ERROR line with the error type and the first line of the driver's message, with anything quoted, IP addresses and the parts of the connection string masked. Testing found an older bug: while the database was unreachable, the friendly 500 page itself crashed, because Flask-Login loads the user whenever a template renders, so the visitor got a bare error. It now falls back to a plain page. Tested on a new Neon test branch (`tests-reqlog-20261111`, expires 13 Nov 2026 at 23:59 UTC) with 20 checks. `online-version` is on GitHub now (Eyram pushed it).

- Under the systemd service the audio worker hit `ValueError: need at least one array to concatenate` inside Kokoro on book 72: a page with no speakable text gives Kokoro nothing to say, and the whole book stopped in "processing". Now a page with no letters or digits, or one where Kokoro makes no audio, gets about 5 seconds of silence (short clips make Android drop its media notification). Any other error on a page is logged with the book id and page, retried once, then replaced by the same silence, and the number of failed pages is logged when the book finishes. Pages over 1500 characters are spoken in chunks split at sentence ends. A watchdog thread restarts the worker if it ever stops and re-queues unfinished books. The app's own log messages now reach the journal. Tested on a new Neon test branch (`tests-worker-20261104`, expires 6 Nov 2026 at 23:59 UTC) with 36 checks using a fake Kokoro, plus the auth and book suites, and checked the real Kokoro on empty, symbol-only and very long text.

- The browser and Android Back button now closes whatever is open before leaving the page: a bottom sheet (Add, book options, More, Sleep, Page text, Contents) first, then the full player, which collapses to the mini player with the audio still playing. Opening the player or a sheet adds a history entry at the same address, and closing it any other way (the ⌄ button, a swipe, Escape, a tap outside) steps back over that entry, so Back never needs two presses. This lives in a small `Layers` helper in `static/js/sheets.js`; it stops htmx from reloading the page content when the Back only closes a layer. Tested on the Neon test branch with 65 Back button checks in headless Chrome, plus the navigation and lock-screen suites.

## 3 Nov 2026

Where things stand at the start of the online version:

- Audio now keeps playing while moving around the app. The pages share one shell (`base.html`) holding the only audio element, a mini player, the full player sheet and the bottom bar, and htmx (self-hosted, no eval, no history cache) swaps just the page content. The reader became a player sheet over the current page with a minimise button, swipe down and Escape. Added a Library view (`/library`) and a read-only `/player/<id>` view for the player; `/read/<id>` opens the book over Home. Fixed along the way: CSRF tokens no longer expire after an hour (the shell keeps its token), Continue listening counts a book as soon as it is opened, and a delete during a book's loading can't leave it playing. Tested on the Neon test branch with 30 navigation checks in headless Chrome plus the auth, book, lock-screen and layout suites.

- Redesigned the UI to feel like a music app (dark, clean, cover-led) with the Ubuntu orange accent. The player has a large square cover with a background glow sampled from the cover, a custom seek bar, a Spotify-style controls row (speed, 15 seconds back and forward, play/pause, sleep timer), and Contents, More (voice, jump to page) and Page text sheets. Home has Continue listening (most recently played first), genre filter chips, square cover cards with a progress line and a three-dot menu, and an Add sheet opened from a bottom bar on phones or a floating button elsewhere. All sheets share one small script (`static/js/sheets.js`). The home view now also passes reading progress and the continue-listening list; no routes, models or database changes. Checked with 57 headless Chrome screenshots at four sizes (no layout issues, every sheet closes three ways) and the auth, book and lock-screen test suites on the Neon test branch.

- Added background and lock-screen playback. The reader now fills in the Media Session API (chapter or page as the title, book as the album, author as the artist, square artwork from a new `?size=96|192|512` option on the cover route, with an initials image when there is no cover) and handles play, pause, previous and next page, seeking and position updates from the lock screen. The page change starts the next page inside the `ended` handler on the same audio element, and the next page is buffered by a hidden audio object halfway through the current one, so in headless Chrome the next page started without any new request to the server. Tested on the Neon test branch: 10 cover checks and 29 browser checks, plus the auth and book suites. A real phone still has to be checked by hand.

- Made the whole UI work on phones and tablets (layout, CSS and a little drawer JavaScript only; no routes, models or behaviour changed). On the reader, the contents sidebar is now a slide-up drawer on screens up to 900px wide, the player has large Prev/Next buttons with speed, voice and jump to page in a grid, and the page text is collapsed by default on phones. Touch screens get 16px inputs and 44px tap targets. Checked every page in headless Chrome at 360x640, 390x844 and 768x1024 with an automatic audit (no sideways scrolling, overlaps, clipped controls, small tap targets or small input text), and compared desktop pixel by pixel with screenshots taken before the change: identical apart from the moving audio playhead.

- Changed the planned hosting address to `waudible.eyramwilson.dev` (it was `waudio.eyramwilson.dev`).

- Prepared WAudible to be served from the internet (step 5, app side). It now runs under gunicorn (one worker process, four threads, 120 second timeout) on 127.0.0.1:8000 only, started by `run_prod.sh` or the systemd unit in `deploy/`. The audio queue starts inside the gunicorn worker and re-queues unfinished books. Added ProxyFix for the tunnel's headers, debug off by default, Secure/HttpOnly/SameSite=Lax cookies, security headers with a CSP, rate limits with Flask-Limiter (login and sign-up 10 per minute, uploads 20 per hour, per real client IP) and friendly error pages. Eyram ran the WAV to MP3 conversion, so the script is deleted. All three test suites (139 checks) pass on the temporary Neon branch. Not installed yet: the systemd service and the tunnel.

- Shrank audio storage (step 4). Pages are now MP3 (mono, 64 kbps, made with ffmpeg) instead of WAV, about 17% of the size: a 3-page test book went from 1647 KB of WAV to 276 KB of MP3. Audio is generated once per voice at speed 1.0, and the reader changes speed in the browser, so a speed change no longer generates new audio. Added `convert_wav_to_mp3.py` to convert the existing WAV files; on a copy of book 68's first 9 pages it turned 76.1 MB into 12.7 MB.
- Tests now run against a temporary schema-only Neon branch instead of production. The test process gets the branch's connection strings in its own environment, and `.env` keeps pointing at production. Branch `tests-mp3-20261103` expires on 4 Nov 2026 at 23:59 UTC.

- Made books private per user (step 3). Books and reading progress now live in the `books` and `progress` tables, and every file is stored under a random `storage_key` (`data/books/<key>.pdf`, `data/covers/<key>.<ext>`, `data/audio/<key>/`). Routes use book ids, every route except login and register needs login, and another user's book returns 404. Uploads are limited to 100 MB, must really be PDFs, covers must be real JPG, PNG or WebP under 5 MB, and each user can have 20 books.
- Replaced the thread per book with one worker thread and a queue, so books are processed one at a time in upload order. Progress is saved to the database after every page, and unfinished books are re-queued on startup.
- The running app no longer uses `book_sessions`, `app/db.py` or `app/session_manager.py`. They stay in place until Eyram confirms after testing. The two old local books are still on disk but not in anyone's library yet.
